# CHANGELOG FLUXPOS FOR [DOLIBARR ERP CRM](https://www.dolibarr.org)

## 1.8.2

- Fix (**in mobile mode the text of the not-selected tab was not visible**): the step navigation took the text color of the theme header ("text of the header menu" - white on a dark header). On the light background of the step navigation that white label disappeared, only the selected tab stayed readable. The step tabs now use fixed readable colors (dark text, the selected tab on a light grey background), independent of the theme; the same colors are also in the critical inline layout, so an old stylesheet copy cannot bring the problem back.
- Fix (**the amount of the cart was shown several times, with the euro sign alternately in front and behind**): on the cart step of the mobile layout the total existed three times (in the step navigation, in the header of the cart table and in the sticky footer), and the local renderer and the server fragment disagreed about the position of the currency symbol - the locale of the browser (via `Intl.NumberFormat`) puts `€` in front for some languages while the server puts it behind for others, so the amounts jumped from side to side on every re-render. Now:
  - the offline renderer formats amounts exactly like the `price()` function of the server (same symbol position, same decimal and thousand separators; index.php sends them from the language of the Dolibarr installation);
  - on the mobile cart step, the amount shows **once**, in the sticky footer of the cart - the copies in the step navigation and in the header of the cart table are hidden there (the summary in the step navigation keeps showing on the products step).
- Module version 1.8.2.

## 1.8.1

- Fix (**the cart shifted up and down on every product added**): the synchronization status pill above the cart existed only while it had a message ("1 order waiting" while a tap was being confirmed, gone again a second later) - its appearance and disappearance moved the whole cart. The pill now exists always with its height reserved: idle it is invisible, offline red, pending orange, and the cart no longer moves.
- Fix (**products without an image were re-requested on every product added**): the thumbnails of a cart line ask the server for the product image, but a product without an image has no answer to give - and every render of the ticket (every addition) repeated the request. A failed image is now remembered in the session (tab) and its request is not repeated; a product that got an image during the session asks for it again on the next ticket of the session (or in a new tab).
- Fix (**the deposit lines of Deposito were shown above the drinks**): the cart shows the newest line first (newest line at the top, like the server screen reversed), and the automatic deposit lines, written by the triggers of Deposito after the drink lines, were therefore at the top of the ticket. They now always print at the **bottom**, after the products (like on a deposit receipt).
- New (**payment footer of the custom layout like the default mode**): with `FLUXPOS_PAYMENT_BLOCK<term>` configured, all buttons used to share one small row. Now the payment items (`pay`, `paymodes`) render as the **large payment grid** of the default mode (2 columns, big buttons) and the other items (`new`, `freezone`, `direct`, `print`, `actions`) as the **small row** below or above them; the configured order is kept (buttons are grouped into consecutive runs of payment and quick items).
- Module version 1.8.1.

## 1.8.0

- New (**shared open tickets, two-way synchronization by operations**): the open ticket of a place can be handled from several devices (devices that share tickets use the same terminal number). The terminal no longer sends copies of its cart: every tap, +/-, quantity pad or removal is an **operation** with a unique id, kept in an outbox per ticket and applied **once** by the new endpoint `applyOps`, which answers the full ticket. Operations are changes, so the changes of several devices on one ticket add up instead of overwriting each other. The screen always shows the last state of the server with the operations not confirmed yet on top of it, so a tap made while a request is on its way can no longer disappear. Other devices read the ticket every 4 seconds through the new endpoint `getTicket` (it answers "unchanged" while nothing changed). Changes made by the screens of the server (payment popup, discount, free line, price or discount pad, customer) are read back after every fragment of invoice.php.
- New (**pay offline, also a ticket that is on the server**): offline, the ticket becomes a sale with its own id (booked exactly once, as before). The sale carries the operations the server had not confirmed yet: at booking, the server applies the ones it had not applied (once, by their ids), then takes the sold quantities off the ticket product by product - what another device added meanwhile stays open. A ticket left empty is removed. The till is no longer blocked when the connection drops before the customer pays, and an offline payment never waits for a sending in progress.
- Lines already sent to the kitchen or bar printer are ordinary lines of the ticket (charged and booked offline too); a new tap of that product starts a new line, as on the server.
- The offline payment asks and books the products and their deposits; free lines and discount lines stay on the ticket (the cashier is asked first).
- New (**sales to check**): an offline sale is marked to check (`llx_fluxpos_sale.status` = 1 with a note) when its ticket was already closed elsewhere (possibly paid twice) or when the booked total differs from the total the terminal charged.
- Change (**Deposito**): the automatic deposit lines (`deposito_auto` > 0) are written by the Deposito triggers on the server only; the catalog carries the deposit data of every drink, so the terminal shows the deposit lines of the operations not confirmed yet. A deposit product sold by hand (a crate, a deposit alone) is an ordinary line. Returned empties are counted as a positive number on the terminal and kept negative by Deposito.
- A change of a line that is gone on the server (removed or paid on another device) never reopens the ticket; a direct payment no longer draws the old ticket over the receipt; changes made by version 1.7 and not sent yet are kept at the upgrade.
- Removed: the set mode, sending the whole cart, reading the cart back from the screen (adoption, snapshots) and the mirror rows for deposit lines.
- Fix: a terminal without tables (place "0") was refused by the synchronization ("Bad request").
- Fix (security): the place sent by a terminal is cleaned before it is used in a reference or in SQL.
- Fix: when a ticket has the same product on two lines, a change goes to one line and never doubles the other.
- New tables `llx_fluxpos_op`; new columns `status` and `note` on `llx_fluxpos_sale` (update_1.8.0.sql).

**After updating:** disable and enable the module once, so the new table and columns are created. Until then the changes of the terminals stay in their outbox.

**Known limits:** offline, the price or discount of a line cannot be changed (the quantity can); free lines and discount lines of a ticket cannot be booked by an offline sale (they stay on the ticket, the cashier is asked first); invoice date, payment date and the cash closing check use the moment of synchronization.

- Module version 1.8.0.

## 1.7.1

- Fix (**products captured offline disappeared from the view when the connection came back**): the `online` event reloaded the order fragment of the server after every recovery attempt, even when the local cart had just been re-sent and the server did not hold it yet (or the send failed) - the ticket on the screen was replaced by the stale order of the server, then the captured products "reappeared" when a payment forced their synchronization again. Worse, after that reload every new product disappeared a second later and the cart cleared: the refresh was followed by a new render cycle whose push erased the lines. Both are gone: after a recovery the terminal now only reloads the server fragment when its own cart is empty, and the set semantics are **stricter** - set mode (lines removed, quantities lowered) is only used once the server has answered the exact content of the cart (its answer mirrors the line ids and prices back); a cart adopted from a screen or from a snapshot of the order merges additively first, so a stale image of the order can never erase the lines on the server. The order of the capture is also corrected: the lines currently displayed on the screen (their freshest image) are adopted before the cached snapshot.
- Fix (**deposit lines of the Deposito module are added automatically to the ticket now**): the deposit lines are written on the draft by the triggers of the Deposito module (a deposit line per sold drink, plus its returned empties), so they were never in the capture of the terminal - and the set semantics of the unified flow then deleted them from the draft again on every synchronization. Two changes: the set reconciliation never deletes a line whose product is a deposit product of Deposito (its quantity follows the drink lines exactly through the triggers of that module), and the answer of every synchronization returns the **label** of every line so lines the terminal did not capture itself are **mirrored into the local cart** and displayed in the ticket like any other line (marked as server-owned: no +/- steppers, quantities never sent back - the server owns them). The ticket of the terminal and the draft of the place now show the same lines and the same total, the deposit charges included.
- Fix (**the noisy information texts in the cart are gone**): the cart showed up to five explanatory paragraphs (order adopted, order synchronized in background, order stored offline, empty-cart hint, Deposito note, last-sale note). The ticket is now only the ticket: same lines, same total as the server. The connection state stays visible in the status pill of the top bar; the stored-offline note remains only while a validated sale is still waiting offline. If the terminal still shows stray text in the cart, please send the screenshot again.
- Module version 1.7.1.

## 1.7.0

- New (**offline and online are one flow - the local cart is always the ticket, online it is synchronized instantly**): the split between the online flow (the server fragment rendered by invoice.php) and the offline flow (the local cart of the terminal) is gone. There is no mode switching and no cart switching anymore: **every** tap and every quantity change goes into the single local cart of the place (IndexedDB), exactly the same offline and online. When the terminal is online, each change is pushed to the server draft **immediately** (debounced, and every push answers with the exact line ids, quantities and totals of the server order, so the local cart mirrors the server draft down to the line); when the terminal is offline, the same cart stays local and the existing background sync replays it when the connection is back - the flow after the network is lost or restored does not change at all.
  - The cart is pushed in **set semantics** whenever it mirrors the full server order (after an adoption or a first successful sync): products removed from the cart are removed from the draft, quantities are set exactly (also lowered). A cart that was captured fresh without the order of the screen is still pushed additively, so server lines can never be wiped by a partial capture. Manual lines, free lines, supplement lines and deposito lines on the server are never touched by either reconciliation.
  - Every server-driven change of the ticket (line edited on the server via the popup pads, discount, invoice-level changes, refresh) is read back into the local cart (`replaceCartFromScreen`), so the cart and the screen cannot diverge.
  - Payments (cash, cheque, credit card, More) wait for the pending synchronization before they open: the payment screens always read a draft that matches what the user sees. `New` and a completed payment clear the local cart as well as the server order. Reducing a quantity below the server value and removing lines are therefore representable at last - the raise-only restriction of the adopted lines is lifted.
  - The popup line pads (per-line quantity, price, discount, weighing) require a line that exists on the server; a line not synchronized yet closes the pad with a note instead of sending a bogus line id.
  - Offline: unchanged behavior - an order registered on the server still cannot be paid offline (it would be paid twice), the alert says so.
- Module version 1.7.0.

## 1.6.2

- Fix (**a product tapped while offline was refused, still adding nothing**): a tap could only become a line of the local cart when the product was found in the catalog that the terminal cached while online. When that cache was missing, incomplete or stored under another third party of the screen, every tap hit the only remaining hard dependency of the offline flow and was refused with the "not in the catalog cached" alert. A tap now never depends on that cache: the label and the price are read **from the product tile that was tapped** (the same tile the user sees, formatted amount parsed by a tolerant separator parser that understands both the European and the US formatting). The cached catalog stays the primary source (it holds the better reference and label data), the tile is the fallback - the tap is captured in every case, since the background merge only sends the product id and the quantity anyway (the server recalcutes its own lines and prices). The refusal alert now only happens when truly nothing about the product can be read at all. The amount parser is extracted as the shared helper `FluxPosOffline.parseAmountText()` (also used by the adopted-from-screen parser).
- Module version 1.6.2.

## 1.6.1

When the theme variables are not defined on the screen, the background became transparent and the text inherited the tile color - on the white tile that is invisible or unreadable (compare: the badge showed blue, then plain black price text, then white-on-white depending on the context). Fix on three levels:

  - the responsive wrapper is defined in this stylesheet too, so an over-wide table scrolls instead of being silently clipped;

## 1.6.0

- New (**offline works like online, in one ticket**): the offline mode no longer forks into a second, "separate" order. Whatever is captured on the terminal while offline - on an empty place or on a place with an order registered on the server - stays one order and is synchronized in the background: as soon as the connection is back, an background sync replays the captured products into the draft invoice of the place on the server (quantities raised to the captured ones, the prices and discounts of the server lines are kept; add lines are added on top), exactly like a ticket built while online. The caller never has to press New or pay twice: captured products flow into the online ticket automatically.
  - The order shown on the screen is adopted into the local cart even when no snapshot of it was cached before the connection dropped: the lines displayed on the screen are read back (product ids, quantities, totals).
  - "New" while offline only discards the order captured on this terminal (nothing unsent is synchronized); the order on the server stays intact and is shown again with its merged lines when the connection is back.
- Fix (**offline cart layout**): the offline cart rendered a table of its own with foreign classes, so the layout of the cart changed as soon as the terminal went offline. It now renders the exact same markup as the online order of the server (same wrapper, same table id and classes, same header columns Disc. / Qty / Total, same line classes, same sticky total): offline and online look and behave the same.
- New (**the line total is the tap target of the unit price**): 1.4.0 removed the Price key from the line-edit popup, which left the unit price of a line without any entry point. The total of each cart line is now tappable like the Qty and Disc. cells and opens the line-edit popup on the price mode (changes the unit price of the line; the discount of the line is already on the Disc. cell). Not shown when line editing is not allowed.

## 1.5.0

- New (**compatible with Deposito, the deposit on returnable packaging module**): a sale that needs no code change was already covered - FluxPos creates its receipts through the standard invoice class, so the Deposito trigger adds the deposit line of every product that names a deposit product, follows the quantities and forces 0% VAT / no discount on deposit and leeggoed lines, and FluxPos receipts are recognised by Deposito from its 0.2.5. Two gaps are closed now:
  - **Returned empties are no longer blocked by the terminal stock guard.** With FLUXPOS_QTY_IN_STOCK enabled, adding or raising a leeggoed product that is not (yet) in stock was refused with "stock is not enough" - although a return puts the empties back INTO stock at validation. Leeggoed products (Deposito field: Leeggoed ticked) are now exempt from that guard on the addline and the merge-into-same-line paths.
  - **The offline cart says what the server will book.** The offline cart lives on the terminal without the deposit lines the server will add, so its total can differ from the booked total (the payment is capped to the booked amount server-side, money is safe). When the Deposito module is enabled, the offline view shows a notice that deposit charges and returned empties are applied server-side.
- New **docs/DEPOSITO.md**: how to run Deposito with FluxPos (products, behaviour at the till, credit notes for empties-only sales, the offline caveat).
- Module version 1.5.0.

## 1.2.2

- Bug fix (**root cause of the whole stacked-layout saga found**): the container of the POS layout printed its class without a separating space since 1.1.0 - `class="posmainwithhead"` instead of `class="posmain posmainwithhead"`. CSS class selectors match whole tokens, so **every rule that starts with `.posmain` never matched anything**: not in pos11.css.php, not in the inline critical block, not the media queries, and in the JavaScript guards. The page has been rendering itself as plain block stacking (cart below the products) since 1.1.0, and every subsequent stylesheet cache fix was correct but irrelevant: the selectors were dead on arrival. The 1.2.1 self-diagnosis strip exposed it in one go: screen 1920x1083, posleft yes, cartcolumn yes, inline critical css yes - and posmain **missing**, which is impossible for a descendant unless the class token itself is wrong. The markup now prints `posmain posmainwithhead` as two separate tokens.
- Safety: `FluxPosRepairLayout` now also **self-heals** any page that still carries the broken token (adds the `posmain` class when the browser only finds a `[class*="posmain"]` element), so terminals on a stale cached page get the working layout without waiting for a clean reload.
- The diagnosis strip is **slimmed down as promised**: on a healthy desktop screen there is no strip anymore, only a line in the console; the fixed bar appears only when something is actually wrong (and then reports the facts). On a narrow screen the mobile step-through note stays in the console as before. Module version 1.2.2.

## 1.2.1

- Bug fix (decisive attempt): the stacked layout survived even the inline critical CSS (1.1.8) and the mobile step-through (1.2.0). The two-column layout is now **forced with inline element styles** (`display:flex;flex-direction:row;...` with `!important` set directly on `.posmain`, `.posleft` and `.cartcolumn` in the browser itself) - an element style cannot be overridden by any stylesheet copy in any cache, theme or other module, so the stacked result is no longer possible as long as the DOM has the right elements. The force only applies on a screen of 768px or wider and is cleared below 768px (also on resize), so the mobile step-through keeps working.
- New: **self-diagnosis strip** (temporarily, to find what was actually going wrong): a fixed bar on the very top of the viewport reports the facts of this terminal in plain text - viewport size, whether `.posmain` exists, the computed display and flex-direction, the actual children of `.posmain`, presence of the inline critical CSS and the list of the loaded pos stylesheets. It is attached to `document.body` itself, so it also appears on an old or partially served page, where the former guard (banner inside `.cartcolumn`) was silent exactly when things were wrong. Red strip with a clear conclusion when this page turns out not to be the 1.1+ structure at all (old document served); yellow/confirming strip when the two-column layout is active. This strip will be slimmed down again after the cause is confirmed. Module version 1.2.1.

## 1.1.7

- Bug fix: pressing **New** did not remove the cart: it stayed in the strip of open sales and "only the time changed". The delete action of `invoice.php` (inherited unchanged from TakePOS) does not delete anything of the cart: it empties the lines of the draft invoice and then **keeps the shell**, resetting its customer and even rewriting its creation date to "now" — the date that the strip of parallel sales displays as start time of the sale. So the cart stayed open with a new start time, and the cart of the place could never be removed. The draft invoice of the place is now deleted entirely (lines, extrafields and the LINEBILL_DELETE triggers included) as soon as New is pressed while it is still a draft; on the next tap of a product a fresh draft is created automatically for the place (that creation path already existed, it just never ran while a shell was kept). A cart that the terminal had stored while offline is dropped from the local storage too when New is pressed while online, and the stale snapshot of the deleted server order is removed from the terminal as well, so the offline capture cannot re-adopt an order that no longer exists. Module version 1.1.7.

## 1.1.5

- Bug fix: the console showed `Failed to load .../custom/public/theme/common/nophoto.png. A ServiceWorker intercepted the request and encountered an unexpected error` and it also turned out that the promised network-first serving of the module css/js (1.1.3) was never actually deployed: the rewrite of the fetch handler had silently missed the commit, so the service worker kept running a pure cache-first strategy — this time over the new pos11 filenames, which would have recreated exactly the same stale screen after the next deployment. The 1.1.5 rewrite makes the service worker minimal and safe: module stylesheets and scripts are served **network first** with a cached copy only when the server cannot be reached (now really in the code and verified in the commit), **images are no longer intercepted at all** (product, category and placeholder images and their redirects go straight to the browser HTTP cache, so the nophoto redirect of `genimg/index.php` can never fail inside the service worker again), the unused cache-first helper is removed and a failing cache write can no longer reject a request (it is logged and dropped). Thumbnails that cannot load (for example while offline) hide themselves instead of showing a broken image (`onerror` on the cart thumbnails and the product tiles). The precache list no longer contains the unused `genimg/empty.png`. Service worker cache renewed (`fluxpos-offline-v14`). Module version 1.1.5.

## 1.1.4

- Bug fix (decisive): the POS screen on the production terminal kept running with the old layout although the server files were verified correct — the caches in the chain (browser HTTP cache, LiteSpeed server cache and the service worker of older deployments) all kept copies of `css/pos.css.php` and `js/offline.js` under URLs known for years, and the 1.1.1 cache-buster cannot help a terminal whose cached HTML still links the files without the suffix, or a cache layer that ignores query strings. The two files are therefore **renamed**: `css/pos11.css.php` and `js/offline11.js`. A URL that never existed before cannot be served stale anywhere — even a service worker with a pure cache-first strategy misses and goes to the network. All the POS screens (main screen, payment, floors, reduction, popup) and the service worker precache list now point to the new names; the offline engine recognizes its own script file by the new name when the page global is missing.
